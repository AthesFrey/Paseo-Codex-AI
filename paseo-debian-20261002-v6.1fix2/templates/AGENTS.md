# 项目执行约定

## 任务识别与执行

- 用户要求实施代码、配置或文档变更时，先识别实际项目根目录、Git 状态、manifest、lockfile、入口和相关脚本，再直接完成实现、必要的依赖安装、构建和验证。保持执行路径短，只运行与本次改动有关的检查；不要为了形式重复扫描或运行无关构建。
- 纯聊天、解释、研究和知识整理不创建项目文件，也不初始化 Git 仓库。
- 工作区根目录是 `/srv/proj`。用户未指定位置的新项目创建在 `/srv/proj/<项目名>`，不要把工作区根目录初始化为项目。同一项目的修复、迭代、升级、重构和改名继续使用原项目目录`/srv/proj/<项目名>`，可以根据需要创建子目录。
- 进入已有仓库后先执行 `git status --short --branch`，保留用户未提交的改动。没有有效 Git 仓库时不要猜测提交、SHA 或发布结果，并明确说明阻断原因。

## Git、提交与改动保护

- 用户提出实施请求，即授权代理在相关检查通过后为本次任务创建 Git commit；不需要再次询问是否可以提交。只在确有本次任务的文件改动时提交。
- 只暂存和提交本次任务涉及的文件。已有的无关修改、未追踪文件、密钥、缓存、依赖目录、完整环境文件和临时产物必须保留在原处，不得擅自纳入提交、覆盖、清理或还原。
- 提交前检查工作树状态、完整 diff 和暂存区 diff，确认没有敏感信息或无关内容，并运行与本次变更相关的测试、构建和静态检查。检查失败时不要假称通过，也不要为了生成提交绕过检查。
- 提交信息遵循仓库已有规范；没有既有规范时使用简短、清晰、祈使式描述。按功能边界组织提交，不为凑提交拆分无关变更。
- 不得使用 `git reset --hard`、强制清理、覆盖用户文件、擅自 amend、rebase、强制推送、merge、tag、部署或对外发布。除非用户明确要求，不自动 push、merge、tag、部署或发布。
- 需要 Git 的代码项目才使用 Git；不要在普通目录或当前目录的空 `.git` 占位目录上运行 `git init`。较大的独立任务按需使用 `codex/<任务名>` 分支或 `/srv/paseo/worktrees` 下的 worktree，普通任务无需创建分支。

## 发布与可追溯构建

- 发布必须从包含本次全部发布内容的干净 commit 构建。禁止从 dirty worktree、未提交文件、无法确认来源的目录或绕过发布脚本检查的目录生成发布包。
- 发布前按以下顺序执行：
  1. 完成本次变更并通过必要检查。
  2. 提交所有应包含在发布中的变更，只提交本次任务内容。
  3. 用 `git rev-parse HEAD` 获取完整 commit SHA，并确认构建源就是该 SHA。
  4. 在源工作树或独立干净 worktree 中确认 `git status --porcelain` 为空。
  5. 从该干净 commit 构建；在发布格式支持时记录完整 SHA、版本或引用和产物 checksum。
  6. 校验产物确实由该 commit 生成，并把实际运行的检查和结果如实记录。
- 如果工作树有与本次任务无关的 dirty 改动，只暂存本次任务文件并提交；发布时从该 commit 创建 `/srv/paseo/worktrees/<唯一任务名>` 下的临时干净 worktree 构建，不得提交或删除无关改动。构建完成后只清理本次创建的临时 worktree。
- 如果无法创建干净 worktree、发布脚本要求的来源无法满足、SHA 无法确认或产物无法校验，停止发布并报告具体原因；不要通过修改脚本、忽略 dirty 检查或复制未知文件来绕过约束。
- 发布产物只写入项目已有的 `build/`、`dist/` 等目录。未明确要求时不部署、不推送、不上传，也不自动生成发布 tag。

## 文件、依赖与临时目录

- 文件放在项目已有且可预测的位置。依赖目录遵循项目约定；不要为了省事更换包管理器。
- Python 项目优先使用 `uv sync`/`uv add` 或项目已有 `.venv`；兼容新 Python 版本时使用 `uv python install`，安装目录由环境变量提供。
- Node 项目遵守已有 npm、pnpm 或 yarn lockfile，依赖放在项目约定的 `node_modules` 中。缺少用户级开发工具时可安装到 `/srv/paseo/tools`，并保持项目版本可追踪。
- 缓存、下载物、解压目录、测试 stub、临时日志、临时归档和 Python 字节码只能放在 `/srv/paseo/cache/<项目名>/` 或 `/srv/paseo/tools/`，不得在 `/srv/proj` 或项目根创建隐藏临时目录。临时目录使用唯一任务名；任务结束后删除，只保留需要交付的生成文件。尊重现有 `TMPDIR`、`UV_*` 等变量。
- 允许按项目需要自动安装和运行局部依赖及开发工具。依赖构建失败时先阅读真实错误；不要全局 `sudo pip`，不要修改系统 Python、安装 Docker daemon、请求 Docker socket 或修改 sudoers、防火墙、系统服务和 `/etc`。

## 安装、测试与系统路径

- 测试安装脚本、服务或部署流程时，不得直接修改真实 `/srv/paseo`、`/etc`、`/var`、systemd 或项目目录。使用 `/srv/paseo/cache/<项目名>/` 下的隔离目录、命令 stub 或静态检查；脚本若写死生产路径，先复制到隔离测试副本并重定向路径。
- 测试结束前清理临时目录，并检查项目根没有新增的隐藏文件、缓存或无关产物。
- 只运行与本次修改风险和范围匹配的检查；不要声称未执行的测试已通过。记录依赖文件变化和实际测试结果。

## 安全与输出

- 不得打印 API key、环境变量全集、认证文件、密码或配对链接。用户要求分享日志时只提供与问题相关的片段，并遮蔽敏感值。
- 发现权限、依赖、发布来源或数据安全问题时，先停止受影响的操作并报告具体文件、命令和原因；不要用破坏性操作或隐式授权解决。
